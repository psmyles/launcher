# Decisions

Numbered and locked. Code comments cite them as `(N7)`. Changing one is a conversation first,
then an edit here, then the code. The superseded decisions of the old launcher (D1–D27) are in
[`legacy/DECISIONS.md`](legacy/DECISIONS.md); N15 lists what carries over.

| # | Decision | Why |
|---|---|---|
| N1 | Product "Launcher", installed once per user (`launcher.exe` / `Launcher.app`). Configs are documents with the extension **`.launcher`**; double-click opens them. | Several tools per folder, one runtime to update. `.launch` collides with Eclipse/ROS; `.lnch` reads as "lunch". |
| N2 | Windows and macOS, one codebase. A config may target one OS: `os="windows"` or `os="macos"` in its header. | Separate per-OS files are acceptable and simpler than one file for both. |
| N3 | The config is a single KDL v2 text file: no zip, no sidecar files. Relative paths resolve against the config's folder, never the working directory. | It diffs and reviews in git; a shortcut's "Start in" can't change behaviour. |
| N4 | A declarative skeleton (window, form, layout, `data`, actions made of steps) plus embedded **Luau** (mlua, sandboxed) for logic: `script` blocks, `lua` steps, `(lua)"expr"` property values, and Lua expressions in `if=`, `enabled-if` and `visible-if`. `{name}` and `{env.X}` stay plain substitution. | Loops, parsing and error handling without growing a homemade expression language; the editor and validation keep working on the skeleton. Evaluation still always ends (time budgets). |
| N5 | No embedded shell scripts. `run` starts programs directly (an argument list, no shell; plus a raw `command-line=` on Windows). Repo scripts run through `run`. An `env-from` step captures environment variables from setup scripts (vcvarsall, conda, etc.). | No generated script files (AV-friendly for an unsigned exe), and user input can't inject commands. |
| N6 | Lua gets only the engine's API: no `io`, `os.execute` or `io.popen`. Load-time Lua has a time budget. Lua never runs on the UI thread. Lua errors report `.launcher` file lines. | Every side effect goes through the console, Cancel, logging and dry-run. |
| N7 | Console: every displayed process runs in a pseudo-terminal, which we spawn ourselves: ConPTY via `CreateProcessW` on Windows (raw command lines; Job Object assigned while suspended), openpty on macOS. Output goes through alacritty_terminal and is drawn by an egui view forked from egui_term. Users can type into it. `capture()` uses pipes. Windows GUI-subsystem programs use pipes. | Tools show progress and colours only on a terminal. egui_term spawns its own PTY, and portable-pty can't pass a raw command line. GUI-subsystem exes (Unity.exe) don't attach to ConPTY. |
| N8 | GUI: egui + egui-winit, no web tech. The renderer is our own sokol_gfx painter (N16). Budget: median TTFP ≤ 150 ms on Windows and macOS. There is no exe-size gate (installed runtime); size is recorded. | Immediate mode suits config-built forms and the visual editor. |
| N9 | Trust: a file carrying the Windows "downloaded" mark (MOTW, `Zone.Identifier` ZoneId ≥ 3) or macOS `com.apple.quarantine` needs a trust prompt before any load-time evaluation. Files from git carry neither mark. | A `.launcher` file runs programs. |
| N10 | `requires="x.y"` gates on the runtime version. The last working copy of each config is cached and used, with a banner, when an update breaks it. Authors validate with `launcher check` and the editor; there is no CI. | Updates arrive by pull, and installers can lag behind. |
| N11 | Runs: one at a time per `.launcher` file, via an OS file lock in app data keyed by the file's resolved full path. An optional `lock="<path>"` on an action guards shared resources across files. The config is snapshotted when a run starts, and reloads wait until it ends. Retry resumes from the failed top-level step. | Different files in one folder may run at once. Git branch switches can rewrite the running config. |
| N12 | Visual editor in v1. Luau highlighting via full_moon. Validation via parse errors, selene-lib lint with definitions generated from the Lua API registry, and cross-checks against the config. Edits are text splices at parser spans; the document is never re-printed. | Comments and formatting survive. kdl 6.7's re-serializer drops comments (LESSONS L1.1). |
| N13 | Distribution: an unsigned per-user Windows installer shared internally; a macOS DMG signed with Developer ID, notarized and stapled. Updates mean running a new installer. | Internal tool first. The stable signature keeps macOS privacy approvals across updates. |
| N14 | macOS: the login-shell environment (PATH from `.zshrc`) is captured at startup. A document opened while the app is running starts a new process. | Finder-launched apps lack the shell's PATH. LaunchServices sends a second document to the running process. |
| N15 | Carried over from master (`docs/legacy/DECISIONS.md`): | Proven in the old project. |
|  | ● Every event handler runs under `catch_unwind`, so keep `panic = "unwind"`. An idle window draws nothing. |  |
|  | ● Nothing product-specific in the engine. |  |
|  | ● Auto layout only; the window fits its content unless given a size. |  |
|  | ● `after=stay\|exit\|minimize`. |  |
|  | ● One state file per config, named with FNV-1a; `persist=#false` opts out. |  |
|  | ● Headless CLI runs never write state. |  |
|  | ● Step warnings are modal and pause the run. |  |
|  | ● `{env.X}` syntax, with a lint for `%X%`. |  |
|  | ● A preset value that matches no option is an error. |  |
|  | ● Our own small logging module. |  |
|  | ● One registry (the catalog) feeds the loader, editor, docs and CLI help; generated docs have a test that keeps them current. |  |
|  | ● No `TODO`/`FIXME` comments. Console output never panics. rfd dialogs run on their own thread. |  |
| N16 | Renderer: egui drawn by our own **sokol_gfx painter**: D3D11 on Windows, Metal on macOS (the M0 variant B, moved into `crates/launcher/src/gfx/` in M1). **Device policy on Windows:** the first frame is drawn on WARP; once the window is shown, a background thread creates the hardware device and drawing moves over to it, rebuilding textures from the painter's CPU copies. With no hardware adapter it stays on WARP. macOS uses the system GPU. | M0 ([`m0/RESULTS.md`](m0/RESULTS.md)), median time to first frame: B 43 ms on Windows WARP and 136 ms on macOS, both within the 150 ms budget without patching third-party crates. egui-wgpu took 276 ms (WARP), 296 ms (hardware) and 201 ms (macOS). With two wgpu-hal patches its Windows WARP frame still isn't drawn until ~158 ms, and it can't hold 10 fps on WARP. Hardware first costs ~120 ms of driver start-up (B: 166 ms), but WARP costs ~1.4 cores while the console streams, against 2.5% of one core on the GPU. |
| N17 | The `args` step (master's command-line builder: `format`, `replace`, `dedupe`, `raw`, `pair`, `pairs`) stays declarative, as a step, not a Lua helper. | The plan's default. The editor can edit it field by field, and these are exactly the parts the legacy launcher's command lines need. Lua can still build a command line when a file needs more. |
| N18 | The Lua API (registry: `lua/api.rs`, docs: `docs/lua-api.md`): `values.x` is a control's value (or a computed value, or a run variable) and `fields.x.Key` a field of its chosen option, a data block or a step result; both are read-only views, changed through `set()` and steps. Functions that change something or talk to the user (`run`, `copy`, `write_file`, `ask`, ...) work only during a run; code that runs while a file loads (computed values, option lists, defaults, conditions) has a 5 s budget. An evaluator can only be built from a trust token (`platform::trust`). | `values`/`fields` mirror templates' `{x}`/`{x.Key}`, so one mental model covers both. Loading a file must never change anything (N6), and the type system, not a convention, keeps untrusted files from evaluating (N9). |
| N19 | **One plain vocabulary** in the app, the files and the code: tool, window, control, step, setting, result, add-on, "Always use" / "Let people choose when they use the tool", "Only when…", "Repeat for each…", "If it goes wrong", "Before starting, make sure…". Developer words never reach the app; `plain_words` tests check the add-ons and the editor. The control kinds have the names people asked for: Drop Down Button, Multi Choice Tick Box, Tick Box, Text Input, Number Input, File, Folder, Button, Text Label, Line, Section ("input" is allowed for them). ([`REDESIGN.md`](REDESIGN.md)) | Colleagues couldn't make a one-step workflow; the words were half of why. |
| N20 | **Steps diagram:** cards and arrows laid out automatically, a + between cards, no free placement, no wires, no zoom (it scrolls). The steps are a tree, so files hold no positions. Runs stay one step at a time. | Non-developers struggle with wiring and canvases; files stay diffable. |
| N21 | **Add-ons:** text-only `add-on { }` blocks of steps and lists (KDL). Built in from `addons/*.kdl` (embedded by a build script, so the engine names no product, N15), plus `<app data>/add-ons/`. A broken add-on blocks nothing. Name clashes: built-in wins; between installed ones the higher version, a tie neither. Only built-in add-ons may use `built-in=` (the engine's own steps). | The library grows without Rust; text only so a tool can carry it. |
| N22 | **Self-contained tools:** a tool may carry copies of the add-ons it uses; a carried copy wins over an installed one; built-in add-ons are never carried. | A tool works on any computer. |
| N23 | **Data flows through "Use…" and the window.** Every setting has one **Use…** menu: type a value, what people chose in a control (any control, or a new one), or what an earlier step found (`{step.result}`). A step's result can be **put into** a control (`put "result" into="control"`): a list becomes a Drop Down Button's choices, anything else its value. That is how one button's findings reach another: through the window, where people see them; filled choices are remembered like values. Drop Down Buttons don't fill themselves when the tool opens: a step fills them (`list-from` stays in the format, but the editor doesn't offer it). | A colleague built "get the branches → choose one → switch → get the latest" as four controls and had no way to connect them. |
| N24 | **Scopes:** an add-on step's body runs with only its settings in view; its declared results come back as `{id.result}`. | Add-ons don't leak names into tools. |
| N25 | **The editor owns the file:** tools are printed canonically (`config::print`), strings quoted, scripts kept as raw strings, comments above a node kept as its note. Supersedes N12 for tools. | Machine-written files; clean diffs. |
| N26 | **Editor side by side:** what people see, what it does, settings. Steps are added from the step picker (groups by app, search with everyday words, details; Suggested for this project and What comes next; missing apps shown, marked). Advanced sits in collapsed sections everywhere. | The cause and effect of "Let people choose" is visible; discoverability. "Before starting" lists checks as lines with "Add a check", so the first + is always for the steps (first try with a colleague). |
| N27 | **The window holds controls** (buttons included), in rows of up to 3 that share the width equally; sections and pages hold rows; auto layout (N15). Controls stretch with the window (counted at their smallest for the fit); the label column fits the longest label. No main button: every button looks the same. Arranged by dragging in the editor (above, below, or beside). | Simple to arrange, keeps the window fitting its content. A taller "main" button and a fixed-width form confused the first colleague who tried it. |
| N28 | **Needs** (`needs { app "git" }`) are checked before anything runs, and shown in "Before starting, make sure…". | Plain "Git isn't installed" instead of a failed command. |
| N29 | **v1 files (`launcher` header) are dropped** once the examples are ported (slice 6); until then both load. | Nothing depends on them yet. |
| N30 | **Repeat for each** over ticked choices, files of a kind in a folder, lines of a result, or a number of times (slice 3). | Batch work (models, images, platforms). |
| N31 | **Run view:** a list by default, a diagram on request (slice 5); plain statuses and "Copy details for help". | People running tools aren't developers either. |
| N32 | **The CLI contract** for apps Launcher drives (ours first: Bite, 3D Review): `--version`, long flags, no prompts, exit 0 only when everything worked, `--report <json>`, OSC 9;4 progress. | Steps can report results and progress. |
| N33 | **Safe defaults:** Delete moves to the Recycle Bin or Trash; Copy asks before replacing; add-ons explain known problems in plain words. | Mistakes by non-technical authors can be undone. |

**Revised by the redesign** (see N19–N33): N3 (tools may use installed or carried add-ons), N4 (a
window plus steps from add-ons; Lua under Advanced), N9 (covers add-ons), N10 (the `format` of a
tool and `uses`), N12 (superseded for tools by N25), N15 (two libraries: the catalog and the
add-ons), N17 (`args` is `core.command-line`), N18 (`settings`, results from Luau).
